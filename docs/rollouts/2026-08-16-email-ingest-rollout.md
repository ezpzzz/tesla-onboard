**Step 2 AMENDED (2026-08-17, Workspace Mail design, retention decision D3/D8):** the blanket 30-day R2 lifecycle TTL originally specified for `evhost-email-private` is **superseded**. It is incompatible with the Workspace Mail design's indefinite-retention-by-default decision (`alex-email-inbox-design-20260817-123909.md`, Premises 3 and Dependencies) — a bucket-level TTL would silently expire raw mail out from under a UI that presents itself as a durable archive. Deletion is now exclusively **app-owned**: purge machinery (message-, reservation-, and guest-scoped) and a config-driven, per-workspace retention sweep (`onlyevs_email_integrations` retention-window column, null = forever) run on their own schedule to remove every stored body copy -- the R2 envelope, extracted attachment objects, the search-index row, and the pre-existing plaintext copy in `onlyevs_email_candidates.proposed_state` -- not just the R2 objects, and not via a bucket lifecycle rule. If step 2 was already executed with the old 30-day lifecycle rule in place, that rule must be removed from the bucket before intake enablement — see the new hard pre-enablement gate immediately below.

> **NEW hard pre-enablement gate (added 2026-08-17):** R2 lifecycle configuration must be verified (via provider API, not console screenshot) to match the workspace retention config — i.e., **no bucket-level TTL** unless and until a workspace's configured retention window is itself expressed as a matching bucket lifecycle rule — **before intake is enabled for real traffic.** Skipping this check means the first month of real captured mail silently expires under the very feature (the durable per-workspace inbox) meant to archive it. This gate sits alongside, and does not replace, gates 1–7 in §2.

**Addendum (2026-08-17): message index, attachments, and backfill ship dark.** The Workspace Mail full-content inbox — the private-schema email message index (`private.onlyevs_email_message_index`), extracted-attachment storage (`private.onlyevs_email_attachments`), the `index_backfill` reconciler job that indexes and extracts attachments from already-captured mail, and per-message read receipts — all ship behind the existing `ONLYEVS_EMAIL_WORKER_ENABLED` flag (worker-side) with no new flag introduced. With that flag `false`, none of this code runs against real data; with it `true` in a controlled workspace per step 8 above, the reconciler and parse-time indexing become live for that workspace only, same blast radius as the rest of the parse worker. This is a build-and-ship-dark addendum, not a new rollout step — the product-facing inbox surface remains additionally gated by the counsel checklist (`docs/legal/2026-08-17-workspace-mail-counsel-checklist.md`) before any multi-tenant enablement, per the design doc's Dependencies section.

**Fingerprint allowlist growth is continuous, not a single step:** `EVHOST_TURO_APPROVED_TEMPLATE_FINGERPRINTS` is populated one verified template at a time as real fixtures clear gates 1–3, independent of and typically ahead of steps 10–13. It never gets a bulk/synthetic entry (D5).

Capture procedure — full detail lives in the runbook (`docs/runbooks/inbox-inbound-ingest.md`, §6), summarized here because it gates release sequencing:

1. **Current working method (supersedes the original "forward as attachment" instruction in D1/D3 — the Turo host mailbox already receives Turo mail directly, so no forward step is needed):** in the Turo host Gmail account, search for the needed message using Gmail search operators (e.g. `"trip has been cancelled"` / `"canceled"` for cancellation notices — checking Trash and All Mail, since cancellations are sometimes filed there; `"requested a change"` for guest-initiated pre-approval change requests, distinct from the already-captured host-approved `"You've confirmed"` sub-template). For each matching message: Gmail **⋮ menu → Show original → Download original**, then place the downloaded `.eml` in the fixture folder. **A plain forward destroys the DKIM/SPF/ARC evidence the go/no-go doc requires — Download-original is required, not a forward.**
2. Store captured `.eml` files in the fixture location: the local gitignored `.turo-email-examples/` folder (never git, never copied/moved elsewhere, never containing guest PII in any other repo file).
   - **Decision (Alex, 2026-08-16): CLOSED.** The gitignored `.turo-email-examples/` folder on a FileVault-encrypted machine **is** the approved encrypted test-fixture location referenced by the go/no-go doc's "approved encrypted test-fixture location" phrasing (§ Required evidence). FileVault-at-rest encryption is sufficient; no separate dedicated encrypted volume/container is required. This closes the open question previously recorded here.
   - **Retention note:** raw `.eml` files in `.turo-email-examples/` are deleted when superseded by a better/duplicate sample of the same template, or immediately on guest request. Retention here is about the interim local fixture copy only — it does not change the production R2 bucket's retention posture, which is now (2026-08-17, Workspace Mail build, superseding this note's prior "30-day lifecycle" reference — see §3.1 step 2's own amendment) **app-owned with no blanket TTL**: the bucket is created without a blanket lifecycle rule, and deletion is exclusively performed by the purge machinery and the config-driven per-workspace retention sweep (default: keep forever), never by an R2-side expiry.
3. Real `.eml` content **never** enters git, a PR, or an issue/ticket — this matches D3 (§1) and is restated here because it governs when gates 1–3 can close.
