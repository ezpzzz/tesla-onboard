## 1. Why this gate exists

Per the design (`## Phase 0 — Infra go/no-go`): "Before UI ships: a telemetry go/no-go doc (mirroring the email-ingest rollout doc) verifying the self-hosted Fleet Telemetry collector + Kafka stack receives signals from at least one real fleet car; Fleet API billing verified against Tesla's primary docs; `limit_reached`/3-config contention surfaced as an honest per-vehicle state."

Everything downstream — history (Phase 1), bookends (Phase 2), rollups/charging (Phase 3), location (Phase 4), the page (Phase 5), evidence packets (Phase 6), durable guests (Phase 7) — depends on real signals actually arriving from a real car. Building any of those phases dark (schema + worker logic behind flags, no user-visible surface) is not blocked by this gate — the design's own worktree-parallelization table says Phase 0 "runs in parallel with everything, founder-owned" and blocks UI *merges*, not builds. **What this gate blocks is any UI-phase (Phase 4 onward, and specifically Phase 5's rebuilt vehicle details page) merging to master with real telemetry surfaced to the founder.**

## 3. What is and is not blocked by this gate

- **Blocked until every row above is UNVERIFIED → VERIFIED with attached evidence:** any UI-phase merge to master. Concretely: Phase 4 (location evidence read path), Phase 5 (the rebuilt vehicle details page), Phase 6 (evidence packets surfaced in the Inbox), and Phase 7 (durable guest identity UI) — anything that puts a real telemetry-derived value in front of the founder or a guest.
- **Not blocked by this gate (per the design's worktree-parallelization table — "Phase 0 gate ... runs in parallel with everything, founder-owned; blocks UI merges, not builds"):** building Phase 1 (history table + worker ingestion), Phase 2 (bookend capture logic), and Phase 3 (rollup/charging derivation logic) dark, behind their existing additive-migration and worker-code seams, with full Vitest contract-test coverage as specced in the design's Implementation Tasks (T1–T11 for the non-UI portions). None of that code renders to a screen; it can and should be built and tested now. It must not be wired into any UI surface, and no UI-phase branch should merge to master, until this document's gates read VERIFIED.
- Migrations for the new tables (`onlyevs_vehicle_stats_history`, `onlyevs_trip_bookends`, `onlyevs_trip_evidence_packets`, `onlyevs_guests`, `onlyevs_guest_identity_keys`, home-area columns) are additive-only and can apply independent of this gate — applying a migration does not surface anything to a user and does not require gate closure, matching the email-ingest doc's treatment of its own schema migration (step 1 of that doc's infra ladder, gated on migration cleanliness alone, not the feature's product gates).

## 4. Verification method notes (why each gate resists a shortcut)

- Gate 1 cannot be satisfied by a manually inserted database row — the row's evidentiary value is that it proves the collector → Kafka → worker pipeline moved a real signal end to end. A hand-inserted row proves nothing about the pipeline.
- Gates 2 and 3 cannot be satisfied by the secondhand figures already written into the design doc ("secondhand figures: streaming ≈$0.0001/signal, vehicle_data poll ≈$0.002, wake ≈$0.02" — explicitly flagged there as "verify against primary docs in Phase 0"). Those numbers are placeholders pending exactly this verification, not a substitute for it.
- Gate 4 cannot be satisfied by a Vitest unit test asserting the UI renders correctly given a mocked `limit_reached` status — that only proves the UI code path exists, not that Tesla's API actually reports the state evhost expects it to report. Real API evidence is required at least once.
- Gate 5 cannot be satisfied by a successful OAuth re-consent alone (a green checkmark on the scope grant) — the scope being granted does not prove the endpoint itself works, returns data in the expected shape, or is priced the way gate 3 assumes. The actual data pull is the evidence.
- Gate 6 is a derived row (multiplies gate 2's captured per-call price by the home-area read's call count) and therefore explicitly cannot close before gate 2.
